# M4 · Phase 4.8 — Wire Overlay + Pipeline to Config, via the Sidecar — Implementation Plan

**Parent:** `m4-tasks.md` (Phase 4.8) · **Design:** `../architecture/vendor-transport.md` (the 4.0 decision — read §4 "Recommendation" + §"Key-handoff seam") · **Apps:** `apps/widget` (Tauri) + `apps/backend` (Node).

**Goal:** make the app **own the backend** and stop routing the API key through the renderer. Rust spawns/supervises the Node backend as a bundled sidecar, reads the selected vendors' keys from the Keychain, and hands them to that process via **env** — the webview's `start` message stops carrying `apiKey` and instead carries only the non-secret **provider / language** selection. Live re-config on `config-changed` (already emitted by 4.3). This closes the one real security gap the transport doc named ("secret through the renderer") and drops the manual `npm run backend` step.

---

## Current state (grounded in the code)

The transport is loopback today, but the **key flows through the renderer** and **provider selection isn't plumbed**:

- **`apps/widget/src/main.ts`** — connects to `ws://127.0.0.1:8787` (`WS_URL`), and on live start does `apiKey = await invoke("key_get", { account: PYAI_KEY })` then `ws.send({ type: "start", mode, apiKey })` (lines ~351–408). So the **secret is read into the webview and sent over the wire** — exactly the "key-in-renderer smell." It also only handles the single `PYAI_KEY`, not per-vendor.
- **`apps/backend/src/server.ts`** — on `start`: providers come from **env defaults** (`DEFAULT_STT`/`DEFAULT_CORR`, not the message), and the key is taken from **`msg.apiKey`** (`process.env[stt.requiredKeys[0]] = msg.apiKey`), lines ~153–175. `language` is never passed to `startSession`.
- **`apps/widget/src-tauri/src/main.rs`** — has the config store + keychain (`key_get`, `get_config`/`set_config`, `config-changed`) but **no backend spawn**: the only `std::process::Command` uses are `open` (privacy panes) and `osascript`. The backend is launched **manually** by `scripts/widget.mjs` (root `npm run widget`).
- **`Cargo.toml`** — has `tauri`, `tauri-plugin-store`, `keyring`, etc. **No `tauri-plugin-shell`** (needed for the packaged-sidecar path).
- **`tauri.conf.json`** — `bundle` has no `externalBin` (no sidecar registered yet).

So 4.8 changes three seams: **(1)** the backend reads providers from `start` + keys from env; **(2)** the webview sends selection, not the key; **(3)** Rust spawns/keys/supervises the backend.

---

## Target architecture (from `vendor-transport.md` §4)

```
webview (mic + UI)  ──loopback WS (audio + provider/lang)──►  backend sidecar (Node, packages/core)  ──►  vendors
      ▲                                                             ▲
      │ transcripts / formatted text                               │ keys via ENV (never the renderer)
      └──────────────── Tauri IPC ──────────────────────  Rust core (Keychain, spawn/supervise)
```

Rust is the **secure key holder**; the webview only ever sees audio + transcripts. The Node backend and 100% of the tested `packages/core` stay unchanged in behavior — only *how it's launched and keyed* changes.

---

## Key decisions

1. **Rust owns the process lifecycle.** Spawn on startup (or first dictation), supervise, and **kill on app exit**. Hold the child handle in a `static Mutex<Option<Child>>` (like `CURRENT_TOGGLE`).
2. **Inject ALL present keychain keys at spawn**, not just the selected one. Then switching STT/correction vendors at runtime needs **no restart** — every `*_API_KEY` the user has entered is already in the sidecar's env. (Restart only when a *new* key is added; see step 3d.)
3. **Packaging — the main decision.** In production the `.app` has no Node, so the backend must ship as a self-contained binary:
   - **Recommended:** compile the backend to a single executable (**`bun build --compile`**, or `@yao-pkg/pkg`, or Node SEA) in `beforeBuildCommand`, register it as a Tauri **`externalBin`** sidecar, and spawn it via **`tauri-plugin-shell`**'s `sidecar()` API (handles the bundled path, arch suffixing, and code-signing).
   - **Dev:** spawn `node` against the workspace backend directly (no compile step) via `std::process::Command`, so the edit-run loop stays fast.
   - A single `spawn_backend()` picks the path by `cfg!(debug_assertions)` / an env flag.
4. **Loopback only.** The sidecar binds `127.0.0.1:8787` (already the default); never expose it. Keep the existing `EADDRINUSE` guard.

## Step-by-step

### 1. Backend — read providers from `start`, keys from env (`apps/backend/src/server.ts`)

```ts
if (msg.type === "start") {
  demo = msg.mode === "demo";
  // providers now come from the message (widget config), falling back to env defaults
  sttId  = demo ? "fixture" : (msg.sttProvider ?? DEFAULT_STT);
  corrId = demo ? "mock"    : (msg.correctionProvider ?? DEFAULT_CORR);
  const language = msg.language || "en";

  stt = getSTTProvider(sttId);
  correction = getCorrectionProvider(corrId);

  // Keys come ONLY from process.env (injected by the Rust host, or a dev .env).
  // No msg.apiKey path anymore — the renderer never sends a secret.
  apiKey = stt.requiredKeys[0] ? process.env[stt.requiredKeys[0]] : undefined;
  if (stt.requiredKeys.length && !apiKey) {
    send(ws, { type: "error", message: `Missing ${stt.requiredKeys.join(", ")} — add it in Settings (⚙).` });
    return;
  }
  // …existing ready/session setup, but pass language through:
  session = await stt.startSession({ apiKey: apiKey ?? "", language });
  // correction language is handled by the localized prompts from 4.7
}
```

Delete the `if (!demo && msg.apiKey …) process.env[...] = msg.apiKey` block. The batch path (`stt.transcribeBatch(pcm, { apiKey, … })`) keeps reading the same `apiKey` (now from env).

### 2. Frontend — send selection, not the key (`apps/widget/src/main.ts`)

```ts
async function connect(mode: "demo" | "live"): Promise<void> {
  const cfg = mode === "live" ? await invoke<any>("get_config") : {};
  ws = new WebSocket(WS_URL);
  ws.onopen = () => {
    ws!.send(JSON.stringify({
      type: "start", mode,
      sttProvider: cfg.sttProvider, correctionProvider: cfg.correctionProvider, language: cfg.language,
    }));
    resolve();
  };
}
```

Remove the `key_get(PYAI_KEY)` read and the `apiKey` param/field entirely — the overlay no longer touches secrets. (The capability check for a missing key now surfaces via the backend's `error` message, or pre-check with `invoke("has_key", { vendor })` before connecting for a nicer inline message.)

### 3. Rust — spawn, key, supervise (`apps/widget/src-tauri/src/main.rs`)

**a. State + a plain keychain read helper** (refactor out of the `key_get` command):

```ts
const VENDOR_KEYS: [&str; 4] = ["PYAI_API_KEY","DEEPGRAM_API_KEY","OPENAI_API_KEY","ANTHROPIC_API_KEY"];
static BACKEND: Mutex<Option<std::process::Child>> = Mutex::new(None);

fn keychain_read(account: &str) -> Option<String> {
    keyring::Entry::new(KEYCHAIN_SERVICE, account).and_then(|e| e.get_password()).ok()
}
```

**b. Spawn with every present key in the env:**

```rust
fn spawn_backend(app: &tauri::AppHandle) {
    let mut cmd = backend_command(app); // dev: node …; prod: sidecar (see step 4)
    cmd.env("HOST", "127.0.0.1").env("PORT", "8787");
    for k in VENDOR_KEYS {
        if let Some(secret) = keychain_read(k) { cmd.env(k, secret); }
    }
    match cmd.spawn() {
        Ok(child) => { *BACKEND.lock().unwrap() = Some(child); }
        Err(e) => eprintln!("[backend] spawn failed: {e}"),
    }
}

fn kill_backend() { if let Some(mut c) = BACKEND.lock().unwrap().take() { let _ = c.kill(); } }

fn restart_backend(app: &tauri::AppHandle) { kill_backend(); spawn_backend(app); }
```

**c. Wire lifecycle in `setup()` and on exit:**

```rust
spawn_backend(app.handle());
// kill on quit: tray "quit" already calls app.exit(0); also handle RunEvent::ExitRequested
```

Use `tauri::Builder…build(…).run(|app, event| { if let RunEvent::ExitRequested { .. } = event { kill_backend(); } })` (or a `WindowEvent`/`on_menu_event("quit")` hook) so the child never orphans.

**d. Restart when a *new* key is saved** — in `set_key` (4.3), after writing the keychain, call `restart_backend(&app)` so the sidecar's env includes the new key. (Switching *between already-keyed* vendors needs no restart — see decision 2.)

### 4. Packaging — the sidecar binary (`tauri.conf.json` + `Cargo.toml` + build)

- **`Cargo.toml`:** add `tauri-plugin-shell = "2"`; register it in `main()` (`.plugin(tauri_plugin_shell::init())`).
- **`tauri.conf.json`:** add the external binary + shell scope:
  ```jsonc
  "bundle": { …, "externalBin": ["binaries/verbatim-backend"] }
  ```
  Tauri expects a target-triple-suffixed file (e.g. `verbatim-backend-aarch64-apple-darwin`).
- **Build step:** compile the backend to `src-tauri/binaries/verbatim-backend-<triple>` in `beforeBuildCommand` (recommended: `bun build apps/backend/src/server.ts --compile --outfile …`). `packages/core` is bundled in.
- **`backend_command(app)`** picks the path:
  ```rust
  fn backend_command(app: &tauri::AppHandle) -> std::process::Command {
      #[cfg(debug_assertions)]
      { let mut c = std::process::Command::new("node");
        c.arg(/* workspace backend entry, e.g. apps/backend dist or tsx */); c }
      #[cfg(not(debug_assertions))]
      { /* resolve the bundled sidecar path via tauri_plugin_shell / app.path() */ }
  }
  ```
  *(If preferred, use `tauri_plugin_shell`'s `app.shell().sidecar("verbatim-backend")?.envs(…).spawn()` for both dev and prod and always build the binary — simpler code, slower dev loop. Pick one; the doc recommends the `cfg` split.)*
- **`capabilities/default.json`:** if spawning via the shell plugin, grant the sidecar scope (`shell:allow-execute` / the `sidecar` permission for `verbatim-backend`). If spawning via `std::process::Command`, no capability is needed.

### 5. Scripts — the app owns the backend (`scripts/widget.mjs`, root `package.json`)

- Update `scripts/widget.mjs` so `npm run widget` no longer starts the backend separately — it just runs `tauri dev` (Rust spawns the backend). Keep `npm run backend` as a standalone-dev convenience.
- Add a `beforeBuildCommand` sidecar-compile step (step 4) so `tauri build` produces a self-contained `.app`.

### 6. Readiness (avoid the connect race)

The webview connects to `:8787` on load; the sidecar may still be starting. Either spawn the backend early in `setup()` **and** add a short retry/backoff to `connect()` in `main.ts` (e.g. 5×200 ms), or have Rust poll the port and emit a `backend-ready` event the webview waits for. Retry is simplest.

## Acceptance criteria + verification

- **Cloud (no network / no Mac):** backend unit/smoke — `start` with `{sttProvider, correctionProvider, language}` selects the right providers; with the key in `process.env` a session starts; **no `msg.apiKey` is read**. `npm run typecheck` clean. (Extend `apps/backend/smoke.mjs` or add a small test.)
- **On-Mac (folds into 4.10):** launch the `.app` with **no manual `npm run backend`** → dictation works; the key is **never** in the webview (grep the `start` frame — only provider/lang); switch STT/correction vendors in Settings and dictate again **without restart**; add a brand-new vendor key in Settings → sidecar restarts and that vendor works; quit the app → the backend process is gone (no orphan on `:8787`).

---

## Risks / gotchas

- **Packaging + bundle size + signing** — embedding a Node runtime is the real lift; the compiled sidecar must be code-signed with the app (macOS hardened runtime). Prototype the `bun --compile` → `externalBin` path early; this is the phase's load-bearing unknown.
- **Orphaned process** — if Rust doesn't kill the child on every exit path (crash, ⌘Q, tray quit), a stale backend holds `:8787`. Handle `RunEvent::ExitRequested` + the tray "quit"; keep the `EADDRINUSE` guard as a backstop.
- **Readiness race** — webview connecting before the port is up; mitigate with retry/backoff (step 6).
- **Key change needs a restart** — env is read at process start, so a newly-added key requires `restart_backend`; switching between already-keyed vendors does not.
- **Dev vs prod drift** — the `cfg`-split spawn means dev runs `node` and prod runs the compiled binary; smoke-test the compiled binary before relying on it (don't let dev-only success mask a packaging bug).
- **Windows later (M6)** — sidecar path/suffix + signing differ; keep `backend_command` the only OS-specific seam.

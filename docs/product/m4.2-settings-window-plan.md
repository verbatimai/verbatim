# M4 · Phase 4.2 — Settings Window + Activation Policy — Implementation Plan

**Parent:** `m4-tasks.md` (Phase 4.2) · **Architecture:** `../architecture/desktop-app-windows.md` · **App:** `apps/widget` (Tauri v2 + Vite + vanilla-TS).

**Goal:** scaffold a **second, focusable window** (`settings`) alongside the existing non-key overlay (`main`), so the user can finally *type* into settings. This phase delivers the window, the activation-policy switch, and the rewiring of the gear + tray to open it. It ships only a **minimal** settings page (enough to prove keyboard focus). Real controls (typed keys, provider/model dropdowns, hotkey capture, language) are **Phase 4.7**; the config store + keychain are **4.3**; deleting the old inline panel is **4.9**.

---

## Current state (grounded in the code)

- **One window** `main` (`src-tauri/tauri.conf.json`), reclassed at startup into a non-activating, **non-key `NSPanel`** by `configure_non_activating_panel()` in `src/main.rs` (`to_panel::<SpikePanel>()` + `NSWindowStyleMask::NonactivatingPanel`). App runs `ActivationPolicy::Accessory`.
- **Settings today is inline** in the overlay: `index.html` has a `.settings` panel (`#settings`), toggled by the gear (`#settingsBtn`, `main.ts:417`) and by the tray, which emits `open-settings` → `main.ts:513` opens the card in settings mode.
- **Tray** (`main.rs` setup) has a `settings` item that currently does `main.show()` + `emit("open-settings")`.
- **Keychain BYOK** exists (`key_save`/`key_get`/`key_has`/`key_delete`/`key_save_clipboard`), plus `get/set_toggle_hotkey`, `ax_trusted`, `inject_text`, `copy_text`, `hide_widget` — all registered in `invoke_handler`.
- **Vite** is single-entry (`vite.config.ts` has no `rollupOptions.input`; only `index.html`). `tsconfig.json` already `include`s `src`, so a new `src/settings.ts` is covered. Dev server on `:5175`; `devUrl` matches.
- **Capabilities** (`capabilities/default.json`) are scoped `"windows": ["main"]`.

> Why the split is needed: the overlay is a **non-key** panel by design (that's what lets injected text land in the app underneath). A non-key panel can never receive typed/pasted keystrokes — hence today's clipboard-only key entry. Typing must live in a *different*, focusable window.

---

## Approach & key decisions

1. **Declare `settings` statically** in `tauri.conf.json` (`visible:false`), rather than building it dynamically. It's created once at startup as an ordinary `NSWindow` (only `main` is reclassed to a panel), and `show_settings_window` just shows/focuses it. Closing **hides** it (prevent-close) so reopening is instant — no rebuild.
2. **Temporary activation switch.** Default stays `Accessory`. On open: `Regular` → `show` → `set_focus`. On close/hide: revert to `Accessory`. The overlay panel stays **non-key** throughout (untouched).
3. **Minimal page for 4.2.** `settings.html` ships just a heading + a text `<input>` — enough to prove focus/typing on-device. Real UI is 4.7.
4. **Rewire, don't delete.** The gear (`#settingsBtn`) and the tray `settings` item now call `show_settings_window`. The old inline `#settings` panel and the `open-settings` listener are left in place but become unreachable; they're removed in 4.9. (Avoids a half-migrated UI mid-phase.)

### 4. `src-tauri/src/main.rs` — command, activation switch, close handling, tray rewire

**a. A shared helper + the command:**

```rust
// Open the focusable settings window. Menu-bar apps live as Accessory; to give a real
// window keyboard focus we briefly become a Regular app, then revert when it closes.
fn open_settings_window(app: &tauri::AppHandle) -> Result<(), String> {
    #[cfg(target_os = "macos")]
    let _ = app.set_activation_policy(tauri::ActivationPolicy::Regular);

    let win = app.get_webview_window("settings").ok_or("no settings window")?;
    win.show().map_err(|e| e.to_string())?;
    win.set_focus().map_err(|e| e.to_string())?;
    Ok(())
}

#[tauri::command]
fn show_settings_window(app: tauri::AppHandle) -> Result<(), String> {
    open_settings_window(&app)
}
```

> **Verify:** `AppHandle::set_activation_policy` is available on macOS in the Tauri 2.x in use. If the method resolves on `App` but not `AppHandle` in this version, capture activation changes through a small state holder set up in `setup()`; `cargo build` will tell us immediately.

**b. Close = hide + revert (never quit), wired in `setup()` after the window exists:**

```rust
if let Some(settings) = app.get_webview_window("settings") {
    let app_h = app.handle().clone();
    settings.on_window_event(move |event| {
        use tauri::WindowEvent;
        if let WindowEvent::CloseRequested { api, .. } = event {
            api.prevent_close();                       // keep the window for fast reopen
            if let Some(w) = app_h.get_webview_window("settings") { let _ = w.hide(); }
            #[cfg(target_os = "macos")]
            let _ = app_h.set_activation_policy(tauri::ActivationPolicy::Accessory);
        }
        // Optional (menu-bar feel): also revert on `WindowEvent::Focused(false)`.
        // Tradeoff below — default is revert-on-close only.
    });
}
```

**c. Rewire the tray `settings` item** (replace the `main.show()` + `emit("open-settings")` body):

```rust
"settings" => { let _ = open_settings_window(app); }
```

**d. Register the command** in `invoke_handler![ … , show_settings_window ]`.

## Activation-policy semantics (the one real gotcha)

- **Default `Accessory`** keeps the app off the Dock and non-frontmost — the reason the overlay never steals focus.
- A focusable window needs the app to be **`Regular`** momentarily; otherwise an Accessory app can't reliably take keyboard focus / come forward.
- **Revert on close** is the safe default. **Revert-on-blur** makes it feel more menu-bar-like but can introduce focus quirks (re-activating a hidden-policy window); keep it off unless the on-device test shows it's clean.
- **Side effect:** while settings is open the Dock icon appears (app is Regular); it disappears on close. Acceptable for the menu-bar pattern; the alternative (permanent Dock icon) was rejected in 4.0.
- The overlay panel is **never** made focusable to "fix" typing — that would break injection.

## Acceptance criteria (from Phase 4.2) + how to verify on the Mac

Run `npm run widget` (backend + `tauri dev`) on the Mac. `cargo build` must pass first — Rust can't be compiled in the cloud authoring env.

1. **Both windows coexist.** Overlay orb shows as before; `settings` exists hidden. ✓ when the gear/tray opens a titled window.
2. **Settings takes keyboard focus.** Open settings, click the `#probe` input, type — characters appear. (This is the whole point; it never worked in the single-panel design.)
3. **Overlay still streams + injects while settings is open.** With settings open, ⌥Space over Notes/Slack → dictate → text lands in the target field. *(Nuance to watch: while the settings window is key, the "frontmost app" is ours; confirm the inject path still targets the previously-focused field via the saved-pid/paste route. Flag any regression — this is the subtle risk.)*
4. **Closing settings reverts policy and doesn't quit.** Close the settings window → Dock icon disappears (back to Accessory), the app keeps running (tray still there), overlay still works, and reopening settings is instant.

---

## Risks / gotchas

- **`set_activation_policy` on `AppHandle`** — verify it resolves in this Tauri version (see note in step 4a). Load-bearing for the whole phase.
- **Injection while settings is focused** (acceptance #3) — the genuine unknown. If a dictation started with settings focused mis-targets, document it and gate "dictate while settings open" as unsupported, or ensure focus-capture still uses the pre-settings target. Verify explicitly.
- **Capability scoping** — forgetting `"settings"` in `capabilities/default.json` makes `invoke`/core calls silently fail in the new window.
- **Multi-page prod build** — confirm `dist/settings.html` is emitted by `vite build` and loads under `frontendDist`; dev works via the Vite server.
- **tauri-nspanel** only reclasses `main`; the `settings` window must remain a plain `NSWindow` (do **not** route it through `to_panel`).
- **prevent_close + hide** — ensures the window persists for fast reopen; if we ever `destroy` instead, `open_settings_window` must recreate it.
